# BentoML
```python
import bentoml
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM


@bentoml.service(
    resources={"gpu": 1},
    traffic={"timeout": 300}
)
class QwenService:

    def __init__(self):
        model_name = "Qwen/Qwen2.5-0.5B-Instruct"

        self.tokenizer = AutoTokenizer.from_pretrained(model_name)

        self.model = AutoModelForCausalLM.from_pretrained(
            model_name,
            dtype=torch.float16
        )

        self.model = self.model.to("cuda")
        self.model.eval()

    @bentoml.api
    def generate(self, prompt: str) -> str:
        inputs = self.tokenizer(
            prompt,
            return_tensors="pt"
        ).to("cuda")

        with torch.no_grad():
            outputs = self.model.generate(
                **inputs,
                max_new_tokens=100
            )

        return self.tokenizer.decode(
            outputs[0],
            skip_special_tokens=True
        )
```
## BentoML Worker
another copy of the service running in its own process. every worker will generally load its own copy of the model. BentoML's current documentation says a Service has 1 worker by default, and you can set the number with workers= in @bentoml.service. Each worker is a separate process running the Service code.
The worker is the actual Python process running the service.
__init__() runs inside that worker, so this:
``` python
self.model = AutoModelForCausalLM.from_pretrained(...)
self.model = self.model.to("cuda")
```
loads the model into GPU memory for that worker.

let workers=2, then bentoML creates:
```
                 BentoML
                    |
          +---------+---------+
          |                   |
       Worker 1             Worker 2
          |                   |
      Qwen model           Qwen model
          |                   |
        GPU 0               GPU 0
```
Worker 1 and Worker 2 are separate processes. therefore, each worker executes __init__() and each one loads safe.model. so eventually
Worker 1 -> model copy -> GPU
Worker 2 -> model copy -> GPU
workers make the work process in parallel 
setting workers=4 launches four worker instances, each in its own process.

just add workers=2 in .service(), you do not need to create worker class and do not need multiprocessing code, bentoML manages the worker processes.

If we have 10 requests and 2 workers, each worker can process 1 request at a time
```
Requests:
R1 R2 R3 R4 R5 R6 R7 R8 R9 R10

Workers:
       Worker 1      Worker 2
       --------      --------
          R1            R2
after this then
       Worker 1      Worker 2
       --------      --------
          R3            R4
```
so conceptually:
```
10 requests
     ↓
   Queue
     ↓
 ┌─────────┐    ┌─────────┐
 │ Worker1 │    │ Worker2 │
 └─────────┘    └─────────┘
    ↓                ↓
   R1               R2
   R3               R4
   R5               R6
   R7               R8
   R9               R10
```
but it's not strictly r1 -> r2 -> r3->, it depends on the availability, not a guaranteed ordering. 
if worker 1 processing r1 which takes 10 sec and worker 2 processing r2 which takes 2 sec then after worker 2 finished it takes r3, So requests are generally dispatched to whichever worker becomes available.

Now if there is only one GPU and 2 workers, both workers may use the same GPU, That means two model copies in GPU memory.
Now if there are two GPU and 2 workers, each workers is assigned with one GPU separately. BentoML supports allocating GPUs to individual workers and provides worker_index for identifying the worker
why worker_index? each worker needs to know "Which GPU am I supposed to use?"
BentoML documents the worker index as the identifier for a worker process and shows using it to map workers to different CUDA devices
``` python
worker_index = bentoml.server_context.worker_index
```
then it determines:
Worker 1 -> GPU 0
Worker 2 -> GPU 1
official example:
``` python
cuda = torch.device(
    f"cuda:{bentoml.server_context.worker_index - 1}"
)
```
because BentoML's worker index is 1-based while CUDA device indexing is 0-based.
to know which cuda it's using, we are substracting 1

there is another concept called replicas
```
workers:
ONE deployment
   |
   +-- Worker 1
   +-- Worker 2

replicas:
Deployment
   |
   +-- Instance 1
   |     +-- Worker 1
   |
   +-- Instance 2
         +-- Worker 1
```
Workers = processes inside a service instance
Replicas = multiple service instances


workers isn't necessarily what you need for LLM performance

For LLM serving, there are other mechanisms designed specifically for inference throughput.

For example, BentoML's current documentation discusses asynchronous APIs and LLM serving engines such as vLLM, which can use batching and continuous batching approaches
